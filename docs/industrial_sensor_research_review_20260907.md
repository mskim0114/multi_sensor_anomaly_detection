## 1. 결론과 검토 범위

현재 프로젝트는 **AI Hub 열화 단계 분류 모델의 연구 성과**와 **실제 Jetson 센서 데이터 수집 기반**을 확보했다. 그러나 이 둘을 연결하는 현장 데이터, 입력 스키마, 정답 체계, 사건 단위 평가가 아직 완성되지 않았다. 가장 먼저 해결할 문제는 모델 크기나 최신 논문 도입이 아니라 **어떤 현상을 어떤 증거로 판정할 것인가**다.

단기 연구는 운전 조건과 관측 품질을 고려한 부하·열·입자상 물질 이상 감시로 좁힌다. 중기 연구는 정상 운전 변화와 이상에 따른 센서 반응의 방향·지연·회복을 구분하는 데 집중한다. 지속학습은 이 구분을 유지하면서 정상 변화에 적응하는 후속 단계로 둔다.

검토에서 구분한 근거 수준:

- **코드 확인:** 제공된 ZIP의 현행 `src/`, `jetson_deploy/` 코드에서 직접 확인.
- **문서 기록:** 저장소의 논문·연구노트·실측 보고서가 보고한 값. 이번 검토에서 독립 재현한 성능이 아님.
- **국소 검증:** 순수 함수·합성 반례·수학적 구조를 확인. 실제 학습 모델이나 현장 데이터 실험이 아님.
- **연구 제안:** 아직 검증되지 않은 가설과 향후 실행안.

ZIP에는 `.pt`, `.onnx`, `.trt` 가중치 파일과 원시 trial 데이터가 없다. 실제 학습·추론 정확도 및 5개 baseline 재전처리 재현은 수행하지 않았다. 현재 검토 환경은 x86_64 Python 3.12.13이며 PyTorch가 없고 Jetson도 아니다. 패키지 설치, 센서 접속, 모델 변경, 원본 코드 수정은 수행하지 않았다. 루트 `AGENTS.md`와 `SERVER_WORKSTATION_HANDOFF.md`를 기준으로 역사적 `codex_context/` 복사본과 현행 코드를 구분했다.

## 2. 우리가 실제로 하는 일

### 2.1 기존 AI Hub 연구

입력은 30개 시점의 8개 스칼라 채널과 120×160 열화상이다. 스칼라 채널은 `NTC, PM1.0, PM2.5, PM10, CT1, CT2, CT3, CT4`다. 저장소 문서는 배포 데이터가 1 Hz이고 원 공급자의 내부 10 Hz 자료 집계 방식은 공개되지 않았다고 기록한다.

V2+는 원 신호와 lag 1/5/10 차분을 LSTM에 넣고, 잠재 특징에 SE를 적용한다. 열화상은 프레임별 CNN을 거친다. 두 표현을 연결해 4개 열화 단계로 분류하며 학습에는 가중 CE와 SupCon을 사용한다.

문서 보고 성능은 다음과 같다. 원시 결과와 가중치가 없으므로 재검증 수치가 아니다.

| 항목 | 저장소 보고 값 | 해석 범위 |
|---|---:|---|
| 공개 데이터 부분집합 | 111,870개 시점 샘플 | 독립 실험 횟수와 다름 |
| 학습/검증 윈도 | 9,313 / 1,157 | 30개 시점, stride 10 |
| V2+ macro F1 | 0.9557 ± 0.0006 | 검증 세트에서 선택·평가한 3회 결과 |
| 모델 파라미터 | 약 2.85M | 현행 구조 기준 |
| 위험 단계 재현율 | 66/66 윈도 | 독립 사고 66건 또는 선행경보 30초 보장이 아님 |
| Sensor-only F1 | 0.9513 | 열화상 제외 실험, 동일 통계 신뢰도는 재확인 필요 |

근거: `src/models/v2_plus.py`, `src/data/dataset.py`, `src/data/config.py`, `docs/논문/paper_draft.md`.

### 2.2 현재 Jetson 브랜치

최근 handoff가 기록한 완료 항목은 센서 bring-up, 1 Hz collector, 품질 메타데이터, trial runner, 개발용 정상 baseline, 30초 offline window builder다.

아직 완료되지 않은 항목은 실제 이상 데이터 수집, Jetson 데이터 학습, 현장 모델 스키마, ModelAdapter, CT2~4 실측, 파트너 uploader와 자동 모델 배포다.

| 구분 | 기존 AI Hub 모델 | 현재 실측 시스템 |
|---|---|---|
| 설비/환경 | OHT·AGV 데이터셋 | 로봇 시험 구역에서 사용할 센서 모듈 |
| 스칼라 입력 | 8개 | 모델 관련 실측 5개 |
| 전류 | CT1~4, 서로 다른 측정점 | CT1 하나, 나머지 front-end 없음 |
| 열화상 | 공급자 데이터의 센서·처리 방식 | FLIR Lepton 계열의 실제 스트림 |
| 목표 라벨 | 정상·관심·경고·위험 | 부하·열·입자상 물질 현상, 별도 severity |
| 데이터 단계 | 지도학습 연구 | 개발용 baseline 및 수집 준비 |

현재 baseline은 5 trial×360초=30분의 development/test-mode 데이터다. handoff 기록상 60개 비중첩 윈도 중 49개 valid, 11개 invalid이며 이유는 FLIR stale이다. CT1의 약 0.0196 A nominal 값은 알려진 부하 전류가 아니라 ADC·아날로그 무부하 노이즈를 환산한 값이다. 따라서 정상 로봇 운전 전류나 고장 임계값의 근거로 사용할 수 없다.

근거: `docs/SERVER_WORKSTATION_HANDOFF.md` §§2–6.

### 2.3 2027 현장 역할

독일 Jetson은 로컬 수집과 실시간 판정을 담당한다. 파트너 플랫폼은 raw 데이터의 운영상 저장·전달 경로이며, 한국 워크스테이션은 연구·학습·평가·ONNX export를 담당한다. 한국 서버를 실시간 경보의 필수 경유지로 만들지 않는다. 파트너 제품, API, 네트워크, export 권한 등은 여전히 확인 사항이다.

근거: `docs/DATA_PLATFORM_ARCHITECTURE.md`, `docs/CONSORTIUM_DATA_PLATFORM_QUESTIONS.md`.

## 3. 유지해야 할 좋은 설계

1. CT2~4를 0이나 CT1 복제로 채우지 않고 물리적 부재로 기록한다.
2. `fresh`, `age_ms`, `status`를 보존하여 실제 값이 같은 경우와 오래된 관측을 구분한다.
3. 원시 데이터를 불변으로 보존하고 라벨을 사후 별도 레이어로 관리한다.
4. `phase`, `scenario_id`, `severity_level`을 서로 다른 의미로 정의한다.
5. recovery를 자동으로 정상 판정하지 않는다.
6. 수집과 offline 전처리가 동일한 품질 함수를 호출하고 기록과 재계산을 대조한다.
7. ONNX export 검증과 현장 정확도 검증을 README에서 구분한다.
8. Jetson과 학습 서버의 런타임·역할을 분리한다.

이 기반은 실험 결과가 왜 나왔는지 추적하는 데 유용하다. 특히 센서 품질 정보는 후속 연구의 입력 후보가 된다. 단, 품질 정보가 시험 일정이나 라벨을 대신 알려 주는 우회 단서가 되지 않는지도 검증해야 한다.

## 4. 우선 해결해야 할 문제와 주장

### F01. 기존 4단계와 새 현장의 4개 시나리오는 같은 문제가 아니다 — 최우선

AI Hub의 0~3은 특정 열화 진행 과정에 붙은 단계다. 현장 `normal/overload/thermal_abnormal/dust`는 현상 범주다. 부하 이상과 열 이상이 동시에 발생할 수 있고, 둘 중 하나가 다른 하나의 원인이라고 자동으로 정할 수도 없다.

**조치:** 기존 데이터셋 전용 4분류를 별도 task로 보존한다. 새 데이터는 현상 유무, 정도, 관측 품질, 확인 수준을 별도로 정의한다. 복합 이상을 다룬다면 현상 출력은 multi-label 후보가 된다. 기존 softmax 4개를 이름만 바꾸어 재사용하지 않는다.

센서 관측의 이상, 설비 결함, 작업자 안전 위험은 서로 다르다. 예컨대 입자 증가가 확인돼도 특정 유해물질·발화·노출 위험을 확정할 근거는 별도로 필요하다. 초기 제품 범위는 감시와 점검 지원으로 두고, 자동 정지나 안전 제어의 적합성은 별도 검증 문제로 둔다.

### F02. 검증 세트 재사용으로 일반화 성능이 낙관적일 수 있다 — 높음

`src/train_v2plus.py`와 `src/train_paper_experiments.py`는 val F1로 best checkpoint를 선택한 뒤 같은 val에서 최종 성능을 보고한다. 논문은 이를 한계로 공개한다. 따라서 이것을 숨긴 누수라고 단정할 수는 없지만, 모델·lag·구성 선택에 반복 사용한 점은 최종 성능 해석에 중요하다.

**조치:** 학습 장비 안에서 그룹 기준 내부 validation을 만들고, 향후 평가용 장비·날짜·설치 조건을 동결한다. 지금까지 반복 사용한 기존 validation은 새로운 미사용 test로 바뀌지 않는다. 별도의 최종 데이터가 필요하다. 윈도가 겹치므로 불확실성은 윈도 iid 가정 대신 장비/세션/사건 단위 bootstrap 등으로 계산한다.

### F03. 반복 실험 seed가 모델 초기화 뒤에 설정된다 — 코드 확인

`EXPERIMENTS`의 lambda는 `V2Plus(...)`를 먼저 만든 다음 `run_experiment(..., model, seed=123)`를 호출한다. 그런데 `torch.manual_seed(seed)`는 함수 내부에 있다. 전달된 seed는 이미 생성된 가중치를 통제하지 못한다. 여러 실험을 연속 실행하면 이전 실험의 RNG 상태도 초기화에 영향을 줄 수 있다. 단독 `src/train_v2plus.py`에도 모델 생성 전 전역 seed 설정이 없다.

**조치:** 모델 factory를 전달하고 seed 설정 후 인스턴스를 생성한다. 실제 seed, RNG 상태, split·데이터 버전, 학습 설정, 정밀도, 초기 state hash를 저장한다. 기존 ±0.0006을 의도한 seed별 초기화 실험으로 해석하기 전에 재실험한다. 기존 수치 자체가 거짓이라고 단정하는 것은 아니다.

### F04. TimesNet 비교 구현의 주기 계산이 잘못됐다 — 국소 반례 확인

`src/models/external_baselines.py`는 rFFT 인덱스에 대해 `T // (top_indices + 1)`을 사용한다. DC를 0으로 설정했지만 배열에서 제거하지 않았으므로 인덱스에 1을 더할 이유가 없다. 길이 30, 주기 10의 사인파는 rFFT bin 3이고 이 식은 7을 반환한다.

또한 이 구현은 top-k를 계산하고도 첫 후보의 batch 중앙값 한 주기만 이용하며, 원 TimesNet의 복수 주기 가중 합성과 Inception 블록을 사용하지 않는다. 파일 자체도 simplified version이라고 밝힌다.

**조치:** 수정·재평가하거나 명확히 축약 변형이라고 표기한다. 공식 구현과 같은 데이터·입력 정보·튜닝 예산으로 비교하기 전에는 “TimesNet 자체를 능가했다” 또는 “Transformer의 성능 상한을 증명했다”는 표현을 피한다.

공식 근거: [TimesNet 저자 코드](https://github.com/thuml/Time-Series-Library/blob/main/models/TimesNet.py)는 `T // top_list`와 여러 주기의 가중 합성을 사용한다. 여기서 원문 코드 내용을 길게 재현하지 않았다.

### F05. 현재 V2+는 열화상 순서와 센서–열화상 시간 관계를 표현하지 않는다 — 수학적으로 확인

현행 코드의 융합은 다음과 같다.

\[
z=[z_s;\frac{1}{T}\sum_t f(I_t)],\qquad \ell=W_s z_s+W_T\bar f+b.
\]

센서 표현 `z_s`는 LSTM 최종 상태다. 열화상은 프레임별 CNN 뒤 평균이다. 따라서 열화상 프레임을 순열로 바꾸어도 실수 연산에서는 결과가 동일하다. 부동소수점 합산 순서의 작은 차이는 가능하다. 실제 합성 특징의 수식 검증에서 역순 logit 차이는 약 3.55e-15였다. 이는 학습된 모델 실행 결과가 아니라 구조의 성질을 검증한 것이다.

최종 head도 linear이므로 추론 logit은 두 모달리티의 가산형 점수다. 공동 학습·SupCon은 표현에 영향을 주지만 입력별 비선형 교차 상호작용을 새로 만들지는 않는다. “전류 변화 후 열 발생”, “먼저 열이 오르고 전류가 뒤따름”을 열화상 순서까지 이용해 구분하는 구조가 아니다.

**조치:** 열화상 단독/순서 뒤집기/시간 순열/정렬 오프셋 실험으로 필요한 시간 정보를 확인한다. 그 결과가 뒷받침되면 경량 temporal thermal encoder 또는 지연을 고려한 관계 모듈을 도입한다. 단순히 더 큰 cross-attention을 넣는 것이 결론은 아니다. SE도 128개 잠재 특징의 gating이며 8개 물리 센서의 원인 중요도라고 직접 해석하면 안 된다.

### F06. 열화상 기여가 작은 이유를 해상도 탓으로 확정할 수 없다 — 주장 수정

보고된 sensor-only F1 0.9513과 multimodal 0.9550의 차이는 0.0037, 즉 0.37%p다. 파라미터는 약 0.37M에서 2.85M으로 늘어난다. 현행 `fc_thermal` 하나가 2,457,728개 파라미터를 가진다. 전체 약 2.85M의 86% 수준이다.

이 결과만으로 열화상이 불필요하다고 결론낼 수 없고, 원 센서 해상도가 원인이라는 주장도 입증되지 않았다. 시간 평균, 촬영 위치, 라벨의 센서 의존성, 단일 과열 과정, 온도센서와의 중복 등 다른 설명이 있다. 더 높은 해상도의 FLIR가 자동으로 이득을 키울 것이라는 주장은 가설로 낮춘다.

**조치:** 마지막 프레임, ROI 온도/핫스폿 면적, 경량 공간 pooling, 시간 변화 특징, sensor-only를 비교한다. 각 센서가 제공해야 하는 독립적인 현장 정보를 먼저 정의한다.

### F07. 100% 위험 윈도 재현율은 30초 선행경보가 아니다 — 최우선

현재 학습 target은 30개 라벨의 majority다. 15개 정상+15개 위험인 입력은 `np.bincount(...).argmax()`의 tie 규칙 때문에 정상이다. 위험이 16개가 되어야 이 예제에서는 위험으로 바뀐다. 실제 함수 국소 검증으로 확인했다.

1 Hz에서 이런 target은 상태 전환 뒤 약 절반 윈도가 지난 구간을 학습하게 할 수 있다. 추가로 stride, 확신도 threshold, 연속 판정 횟수, 결측 보류가 경보 시점을 바꾼다. 모델이 항상 그만큼 늦는다는 실측 결론은 아니지만, 윈도 분류 점수만으로 경보 시간을 보장할 수 없다는 반례다.

**조치:** 현재 상태 탐지라면 last-tick target과 비교한다. 미래 위험 예측이라면 관측 종료 후 정해진 horizon 안에 사건이 발생하는지를 별도로 정의한다. 사건 시각, 첫 경보, 최소 개입 필요 시간을 기록하여 lead time 분포를 평가한다. Danger 30초라는 라벨 정의 자체와 모델의 30초 사전 예측을 구분한다.

### F08. AI Hub의 30행이 항상 30초인지는 코드에서 보장되지 않는다 — 조건부 위험

`src/data/session_index.py`는 인접 파일 간 간격이 120초를 넘을 때만 세션을 나눈다. 이후 `dataset.py`는 30행을 취하지만 실제 시간 간격을 검사하지 않는다. 2초 간격의 30개 파일을 만든 국소 테스트에서 한 세션으로 묶였으며 첫·마지막 시각 차이는 58초였다.

실제 AI Hub 원시 자료에 이 공백이 존재한다는 뜻은 아니다. 원시 자료가 없어 아직 모른다. **코드가 이를 막지 못한다는 사실**을 확인한 것이다. 반면 신규 Jetson window builder는 sequence 연속성을 검사한다.

**조치:** AI Hub 전체 timestamp 차이·중복·window span을 집계한다. 연속성 확인 전에 lag 1/5/10을 정확히 1/5/10초라고 단정하지 않는다. 공백이 확인되면 원인과 처리 정책을 먼저 정한다.

### F09. planned intervention이 실제 개입 시각으로 저장된다 — 최우선 수집 수정 후보

`jetson_deploy/scripts/12_run_trial.py`는 `intervention_start_tick/end_tick`를 `plan`에서 미리 복사한다. 실제 진행 중 callback은 phase 시작을 출력할 뿐 작업자가 실제 조작을 수행했는지 확인하거나 그 시각을 기록하지 않는다.

이 필드가 실제 개입 기록으로 해석되면 반응 지연 연구의 기준 시각이 틀릴 수 있다. 종료도 anomaly 마지막 tick 269와 recovery 시작 tick 270의 이벤트 시각 의미를 구분해야 한다.

**조치:** v1 raw를 수정하지 않는다. 다음 스키마에서 planned와 actual event를 분리하고 컨트롤러 로그/별도 조작 이벤트 기록을 연결한다. 실제 여부를 모르거나 확인을 놓친 경우 null/미확인으로 남긴다. 단계 안내음 시각과 설비 입력이 바뀐 시각도 같다고 가정하지 않는다.

### F10. valid_for_training은 모든 센서가 쓸 수 있다는 보장이 아니다 — 정책 경계

`snapshot.py`는 thermal 품질만 윈도 invalidation에 사용한다. NTC/CT1/SPS30 오류는 `model_channel_issues`에 보존하지만 invalidation에 반영하지 않는다고 명시한다. 국소 테스트에서 NTC error+FLIR 정상인 30개 snapshot의 window valid는 True였다.

이는 숨은 구현 오류라고 단정할 수 없는 의도된 현행 정책이다. 그러나 향후 학습기가 `valid_for_training`만 보고 모든 입력이 유효하다고 가정하면 문제가 된다. `legacy_model_ready=false`도 별도로 존재한다.

**조치:** 현행 품질 정책을 바꾸지 않고, 향후 model adapter에 모델별 필수 채널·유한값·status·age 검사와 availability mask 계약을 둔다. 결측 숫자는 모델 tensor 작성 편의상의 placeholder와 실제 관측을 분리해야 하며 raw에 측정값처럼 만들지 않는다. 적용 범위를 벗어나면 정상 대신 판단 보류로 표시한다.

### F11. FFC와 고정 실험 일정은 편향과 서비스 공백을 만들 수 있다 — 높은 연구 가치

handoff가 보고한 FFC stale은 대략 tick 28~31, 211~214에 몰리고 window 7은 5 trial 모두 invalid였다. 이것은 해당 개발 baseline에서의 관측이며 미래 모든 환경의 고정 특성이라는 뜻은 아니다. canonical 개입 구간은 90~269이므로 FFC 손실과 시나리오 내 위치가 결합될 수 있다.

invalid window를 제외한 정확도만 보면 경보가 불가능했던 구간을 감출 수 있다. mask·age·warm-up·trial 상대 위치를 모델에 넣을 경우 시험 일정의 우회 단서로 작동할 가능성도 있다.

**조치:** 기존 v1 수집·FFC·raw 보존 정책은 유지한다. 별도 평가에서는 전체 시간 중 유효 판정 비율, 보류 시간, FFC 동안 사건 누락을 포함한다. 향후 변경 승인을 거친 별도 protocol version에서 개입 타이밍이 다른 검증 trial과 sham control을 설계한다. v1 자료를 조용히 재라벨링하거나 보간하지 않는다.

### F12. 1 Hz master jitter와 센서간 동시성은 다르다 — 지연 연구 전 확인

collector는 CT의 약 0.5초 burst, NTC 순차 측정, worker의 최신 SPS/SCD/FLIR 관측을 하나의 snapshot으로 묶는다. CT와 NTC 관측은 `age_ms=0`으로 생성된다. master tick이 정밀하더라도 센서들의 물리적 관측 시간 구간이 같다는 뜻은 아니다.

또한 CT의 `actual_sample_rate`는 읽기 수/수집 소요 시간으로 산출한다. 독립적인 ADC 변환 수·샘플별 시간 균일성이 검증됐다는 의미까지 확장해서는 안 된다.

**조치:** 반응 지연 추론 전에 센서별 관측 완료 시각·집계 구간·응답 특성을 확인한다. 알고리즘이 찾은 lag를 바로 물리 인과 지연으로 부르지 않는다. 현재 설정을 바꾸기보다 알려진 입력과 참조 측정으로 측정 체인을 검증하는 것이 우선이다.

### F13. 논문 지연 수치는 최신 실측 기록과 다르다 — 즉시 문서 정정 후보

논문에는 Jetson 약 5ms 추정과 sub-10ms 충족이 남아 있다. 최신 환경 문서의 서로 다른 측정 항목은 다음과 같다.

| 경로 | 문서 기록 | 주의 |
|---|---:|---|
| ORT CUDA EP | 16.27 ms/sample | 해당 실행 조건의 실측 기록 |
| ORT CPU EP | 46.45 ms/sample | 해당 실행 조건의 실측 기록 |
| standalone TensorRT FP32 | GPU compute 평균 4.88 ms | end-to-end 지연과 다름 |
| standalone TensorRT FP16 | GPU compute 평균 3.33 ms | 정확도 회귀·서비스 통합 성공과 별개 |
| ORT TensorRT EP | 첫 run에서 SIGSEGV 기록 | available과 실제 실행 성공 구분 |

**조치:** hardware/runtime/batch/warm-up/전처리 포함 여부가 같은 표로 다시 보고한다. 16ms가 1Hz 감시에 충분할 가능성과 “Jetson에서 10ms 미만을 증명했다”는 주장은 별개다. 실제 센서 반응→윈도→모델→경보 전체 지연을 측정한다.

근거: `docs/JETSON_ENVIRONMENT.md` §§9–12.

## 5. 관련 연구의 역할과 한계

### SensorLM

SensorLM은 센서–언어 정렬을 위해 통계·구조·의미 설명을 활용하며, 웨어러블 데이터에서 분류·검색 등을 검증한다. 제조설비로의 직접 전이는 별도 검증이 필요하다. [원문](https://arxiv.org/pdf/2506.09108)

우리 적용 후보는 “센서 파형→그럴듯한 고장 문장”이 아니라, **실측 구간→운전 맥락→점검 근거의 연결**이다. 통계적 기술은 수치에서 만들고, 원인·조치 설명은 확인된 로그와 전문가 기록에서 얻는다. LLM이 생성한 고장명을 물리적 정답으로 되먹이지 않는다. 온라인 모델 입력에 미래 정비 결과가 들어가면 안 된다. 사후 정보는 label/학습 자료로만 구분한다.

### GlucoFM

느린 추세와 짧은 변동의 분리, 관측 마스크 보존, 잠재표현 예측이라는 설계가 참고 대상이다. 혈당의 일 단위 표현과 평가를 산업 실시간 탐지의 검증으로 대신할 수 없다. [원문](https://arxiv.org/html/2605.30865)

우리 적용 후보는 센서별 시간 규모·결측·관측 나이를 보존하는 경량 표현이다. 느림=정상, 빠름=이상으로 해석하지 않는다. 평균 제거나 증강이 점진적 고장 신호를 지우는지 확인한다. causal filter를 사용했다는 사실만으로 전체 encoder·정규화·평가까지 실시간 인과적이라는 결론을 내리지 않는다. 관측 종료 뒤 데이터를 볼 수 없는 평가를 별도로 수행한다.

### Fast Weight Attention for Continual Learning

이 연구는 고정 크기 recurrent memory의 국소 갱신을 학습 규칙으로 해석하고 시간 정렬·가소성·망각을 구분한다. 주요 검증은 산업 열화 진단이 아니다. [원문](https://arxiv.org/pdf/2608.27763)

우리 적용 후보는 정상 운전 맥락의 제한적 적응이다. 본체 가중치를 계속 재학습하는 것과 forward-pass memory 갱신을 구분한다. 비교 대상은 고정 모델뿐 아니라 단순 EMA/NLMS/RLS나 작은 recurrent memory도 포함한다. 모든 센서 변화를 메모리에 쓰는 모델은 고장까지 정상화할 수 있으므로 “예측 오차가 줄었다”만으로 성공 판정하지 않는다.

### 신규성 판단

온라인 이상탐지·분포 변화 적응 자체는 기존 연구 영역이다. 예를 들어 [IIoT 적응형 이상탐지 연구](https://arxiv.org/html/2601.03085)는 이 문제를 다루지만 평가 데이터는 주로 네트워크 자료다. 따라서 산업이라는 제목만으로 우리의 기계 반응·현장 센서 문제와 동일시하지 않는다.

다중 시간 규모, 마스킹, 언어 정렬, fast memory를 결합했다는 것만으로 최초라고 주장할 수 없다. 아래 가설별로 기존 방법이 같은 데이터 조건·관측 제약·평가 기준에서 무엇을 해결했는지 더 좁혀 비교해야 한다. 이번 검토는 포괄적 신규성 조사나 최초성 증명이 아니다.

## 6. 제안하는 연구 질문

### 핵심 질문

**운전 조건과 관측 품질이 달라져도, 센서 반응의 방향·지연·회복 관계를 이용해 현장 이상을 더 일찍, 더 적은 오경보로 발견할 수 있는가?**

현장에서 구분하고 싶은 예:

- 정상 부하 변경 뒤 예상되는 전류·열 반응.
- 같은 운전 조건인데 과거와 달라진 열 반응과 회복.
- 열화상만 오래됐거나 오류가 난 경우.
- 입자 증가만 관찰되어 그 이상의 설비 원인을 확정할 수 없는 경우.

### H-A: 관계 정보의 추가 가치

같은 입력 채널·연산 예산·오경보 기준에서, 센서별 독립 표현과 가산형 융합보다 **운전 맥락에 조건화된 반응 관계**가 사건 검출률 또는 lead time을 개선한다.

반증 실험: 시간 순열/정렬 변경에 관계 모델이 민감해야 하며, 원래 정렬에서의 이득이 여러 날짜·설비 조건에서도 유지돼야 한다. 값의 크기나 세션 식별 정보만으로 설명된다면 관계 기여 주장을 기각한다.

### H-B: 관측 품질을 고려한 가용성

실제 FFC·센서 부재 조건에서 품질을 고려한 모델 또는 검증된 sensor-only 경로가, 무조건 완전 윈도만 요구하는 방식보다 **동일 오경보·미탐 제약 아래 유효 판정 시간**을 늘린다.

반증 실험: random dropout만으로 평가하지 않고 실제 FFC 구간과 연속 오류를 포함한다. unavailable 상황에 무리하게 정상 판정을 늘렸다면 실패다. 보류율을 높여 정확도만 좋아 보이게 만드는 것도 실패다.

현재 v1에서 invalid로 정의된 자료를 임의로 정상 학습 자료로 바꾸지 않는다. 별도의 versioned 연구 프로토콜과 model eligibility가 필요하다. 기존 기준 모델과 원시 provenance는 보존한다.

### H-C: 제한적 적응의 효용 — H-A/H-B 이후

정상 운전 변경에는 빠르게 적응하면서 실제 이상이 지속될 때 검출 능력이 사라지지 않는다. 고정 정상 기준, 갱신 보류, 제한적 메모리를 비교한다.

반증 실험: 정상 조건 변화, 진행성 이상, 둘이 동시에 발생하는 경우를 구분한다. 이상 점수 감소만으로 정상 복귀라고 판단하지 않고 독립적인 상태 확인을 유지한다. adaptation 뒤 알려진 이상 사건의 누락이 증가하면 실패다.

### 보조 질문: 설명과 사례 검색의 가치

센서–언어 정렬이 실제 과거 사례 검색과 점검 시간을 개선하는가? 숫자·시간·채널·근거가 맞는지 평가한다. 탐지 성능 개선과 작업자 설명의 유용성을 별도 지표로 보고한다.

## 7. 산업적 실험 설계

### 7.1 관측 가능성 확인표부터 작성

| 항목 | 기록할 내용 |
|---|---|
| 현상 | 부하·열·입자 중 무엇을 관찰할 것인가 |
| 설비/운전 조건 | 장비, 프로그램/사이클, 속도·payload 등 실제 확보 가능한 정보 |
| 센서의 물리적 역할 | 측정 위치, 단위, 범위, 응답·집계 방식 |
| 실제 입력 이벤트 | planned와 actual 시각, 확인 출처 |
| 독립적인 상태 근거 | 참조 계측·운전 로그·점검 기록 중 가능한 것 |
| 반응과 회복 | 관찰 시각, 불확실한 구간, 잔류 효과 |
| 현장 조치 | 작업자가 경보 이후 할 수 있는 확인·점검 |

로봇 소유·운영기관이 정하지 않은 payload, 속도, 가열·입자 발생 방법을 여기서 임의로 정하지 않는다. 확정된 실험 조건을 데이터 기록과 모델 가설로 연결하는 것이 연구자의 일이다.

### 7.2 비교할 조건

| 조건 | 목적 |
|---|---|
| 여러 정상 운전 조건 | 특정 정상 조건만 외우는지 확인 |
| 정상 부하 전환 | 정상 전환에 대한 오경보 확인 |
| 확인된 부하/열/입자 현상 | 목표 현상 검출 |
| 정상과 유사한 크기의 이상 변화 | 진폭만 이용하는 지름길 차단 |
| 실제 센서 stale/FFC | 관측 실패와 공정 이상 구분 |
| 변화 없음+동일 실험 절차(sham) | 안내·시간·작업자 행동 등 우회 단서 확인 |
| 정상 복귀 관찰 | 잔열·잔류 입자를 정상으로 잘못 라벨링하지 않는지 확인 |
| 새 날짜·새 설치 조건·새 장비 | 일반화 검증 |
| 정상 변화+이상 동시 발생 | 적응이 이상을 흡수하는지 확인 |

시뮬레이션 데이터는 방법의 반례·디버깅용으로 유용하다. 실제 고장 관측의 대체 근거로 합산하지 않는다. 필요한 표본 수는 독립 사건 수·변동성과 신뢰구간 목표에 따라 pilot 이후 정하고, 윈도 수가 많다는 이유로 증거가 충분하다고 판단하지 않는다.

### 7.3 split와 시간 정보

split은 장비·날짜·trial·조건을 기준으로 먼저 정한 후 window를 만든다. 같은 trial의 인접 윈도를 train/test에 나누지 않는다. timestamp·trial_id·phase·scenario_id·severity는 관리와 정답 정보이며 무조건 모델 feature로 넣지 않는다. 운전 상태도 추론 시점에 실제 사용 가능한 것만 입력한다.

현행 v1 일정은 보존한다. 시험 일정이 다른 일반화 평가는 후속 버전으로 설계하여 fixed-timing shortcut을 점검한다. baseline도 이전 trial의 잔류 효과가 없다는 근거를 확인하고 정상 annotation을 확정한다.

### 7.4 먼저 비교할 작은 모델

1. 물리적으로 해석 가능한 채널별/운전조건별 통계 기준.
2. 관측 가능한 5개 채널의 경량 sensor-only 분류/탐지 모델.
3. 열화상 통계 또는 작은 공간 인코더를 더한 모델.
4. 시간적 열 반응을 보존하는 모델.
5. 운전 맥락·품질을 고려한 관계 모델.
6. 동일 구조에 제한적 적응을 더한 모델.

5채널 모델은 현재 가장 낮은 구현 위험의 비교 후보이지, 이번 검토로 확정·변경한 스키마가 아니다. raw 재현과 물리 신호 확인 후 정한다. 향후 CT를 추가한다면 단순히 채널 수가 아니라 측정 역할이 맞는지 확인해야 한다.

### 7.5 평가 지표

- 정상 설비 운전시간당 오경보 사건 수. 경보 병합 간격·해제·cooldown을 사전에 고정.
- 이상 사건별 검출률과 첫 경보까지의 지연.
- 정의된 위험 사건까지의 lead time 분포. 미탐은 빠뜨리지 않고 별도 보고.
- 실제 사용 가능 시간 대비 판정 가용률·보류율, 오류/결측 조건별 미탐.
- 단일/복합 현상별 성능과 새 장비·날짜·설치 조건별 성능.
- 재교정·적응에 필요한 정상 데이터 시간, 라벨/점검 횟수.
- 수집→전처리→모델→경보 전체 p50/p95/p99 지연, 메모리·전력·장기 안정성.
- 사건 검출 1건당 점검 부담과 실제 유효 조치 비율.

99% 정상이라는 문서상의 원본 비율을 새 현장 확정 비율로 쓰지 않는다. 현장 prevalence를 측정한다. 짧은 실험에서 오경보 0건이어도 장기간 무오경보를 보장하지 않는다. 안전 목표와 비용에 근거해 수용 기준을 현장 담당자와 정한다.

## 8. 실행 계획과 완료 기준

기간은 작업량 추정이며 원시 자료·로봇 가용성에 따라 달라진다. 달력상 마감과 학회 채택 확률을 임의로 확정하지 않는다.

| 단계 | 작업 | 산출물 / 완료 기준 |
|---|---|---|
| 0. 근거 보존 | 현재 연구와 실측 결과를 구분, 논문 주장 목록 정리 | 검증된 사실/추정/미완료 구분표 |
| 1. raw 재현 | 5개 개발 baseline 전달, 기존 85개 파일 checksum 대조, 공식 window builder 재현 | 5 trial·1800 snapshot·60 window·49/11 일치 및 raw 불변 |
| 2. 기존 연구 복구 | seed 생성 순서·TimesNet·평가 정밀도·split·timestamp audit | 재실행 가능한 설정과 정정된 비교표 |
| 3. 현장 타당성 | 알려진 운전 입력에서 CT·온도·PM·thermal 실제 반응 및 시각 검증 | 관측 가능성 표, 참조 측정 근거 |
| 4. 데이터/라벨 확정 | planned/actual 이벤트, 현상·품질·정도 분리, 독립 trial 수집 | versioned 데이터와 annotation, 고정 평가 split |
| 5. 최소 산업 baseline | 조건별 통계와 작은 sensor-only/thermal 모델 | 사건·오경보·가용률 평가표 |
| 6. 핵심 연구 H-A/H-B | 반응 관계·시간·품질 요소를 통제 비교 | 공정한 ablation, 반증 결과, 적용 범위 |
| 7. 적응 H-C | 고정·무조건 적응·제한적 적응 비교 | 정상 적응 개선과 이상 검출 유지 동시 확인 |
| 8. 현장 병행 운영 | 자동 설비 제어 없이 경보와 실제 점검 결과 기록 | 장기 서비스 유효성, 배포·복구 절차 |

1단계는 handoff의 기존 재현 gate를 따른다. raw가 없는 현재 검토에서 결과를 생성하거나 PASS로 표시하지 않았다. 단순 코드 검토·계획 수립은 수행했지만 현행 수집 정책/스키마 변경은 하지 않았다.

초기에는 TensorRT 수 ms 최적화보다 측정 근거와 사건 경보 지연이 우선이다. 파트너 플랫폼 인터페이스가 미정인 동안 별도 production 서버·업로더 구축도 우선 과제가 아니다.

## 9. 검증한 항목과 남은 불확실성

| 이번 확인 | 결과 | 범위 |
|---|---|---|
| Python 구문 파싱 | 66개 PASS | 역사적 복사본 포함, runtime 통과 아님 |
| NTC error+thermal 정상 품질 함수 | window valid=True | 의도된 정책 경계 확인 |
| 2초 간격 30파일 세션 구성 | 1 session, span 58초 | 실제 데이터 공백 존재 여부는 미확인 |

| TimesNet 주기 식 | 주기 10→7 | 합성 사인파로 계산 식 검증 |
| V2+ 융합식 순서 불변성 | 역순 오차 약 3.55e-15 | 임의 특징에 대한 수식, 학습 가중치 실행 아님 |
| thermal projection 파라미터 | 2,457,728 | 레이어 차원으로 계산 |
| 실제 모델 성능 재현 | 미수행 | raw·가중치·학습 환경 없음 |
| 새 현장의 산업 적용 성능 | 미검증 | 공식 이상 데이터 미수집 기록 |

즉시 필요한 추가 자료는 5개 개발 baseline raw, 기존 결과 JSON/학습 설정/가중치, AI Hub 파일 timestamp 집계 또는 원 데이터 접근이다. 현장 측에는 실제 운전 상태 로그의 가용성, 측정 위치, 참조 계측·점검 근거, 합의된 개입 절차가 필요하다. 이 자료들은 다음 실행 단계에 필요하며 이번 검토 결론을 이해하기 위한 전제는 아니다.

## 10. 최종 판단

현 프로젝트의 강점은 단순히 센서 수나 95%대 점수가 아니다. **관측 출처와 품질을 보존하는 수집 기반 위에서, 정상 운전 변화·설비 현상·센서 실패를 구분하는 실제 데이터를 만들 수 있다는 점**이다.

기존 V2+는 유용한 기준 모델로 보존하되, 논문의 비교·재현·선행경보 주장을 정리해야 한다. 후속 연구는 반응의 방향·지연·회복과 관측 품질을 중심으로 좁히고, 그 효과가 입증된 뒤 제한적 메모리 적응과 센서–언어 연결을 확장한다. 무엇이든 구분하는 모델을 약속하기보다 **어떤 조건에서 구분 가능하고, 어떤 조건에서는 추가 관측이나 점검이 필요한지 증명하는 연구**가 산업에 더 직접적인 가치를 제공한다.
